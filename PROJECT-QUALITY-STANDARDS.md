# 30-Day Portfolio — Quality Standards

These standards apply from **Day 3 onward**. Days 1–2 can be revisited later for visual upgrades.

## Core goal
Every project should look like something that could be shown to a real client or recruiter — not a basic tutorial UI. The first impression should be strong enough to make someone stop scrolling.

## Before coding
- Research 5–10 relevant professional references for the exact project type.
- Use sources such as Pinterest, Dribbble, Behance, and Awwwards for inspiration.
- Study typography, spacing, navigation, card systems, imagery, layout hierarchy, responsive behavior, and theme treatment.
- Use references as inspiration, not as direct copies.
- Decide a clear visual direction before implementation.

## UI requirements
- Client-level visual polish and a strong first screen.
- Clean, intentional typography and spacing system.
- Responsive layouts designed separately for desktop, tablet, and mobile — not simply shrunk.
- Light and dark themes where appropriate, both fully polished.
- Reusable React components and clean file structure.
- Hover, focus, active, empty, loading, and error states where relevant.
- High-quality imagery/mockups appropriate to the project.
- Accessible contrast, semantic structure, keyboard-friendly interactions, and visible focus states.
- Consistent radius, borders, shadows, icon style, and design tokens.

## Quality gate
A project is not considered complete until:
1. Reference research is complete.
2. First impression feels client/portfolio ready.
3. Desktop QA passes.
4. Tablet QA passes.
5. Mobile QA passes.
6. Theme QA passes where applicable.
7. All important screens/states are present.
8. No broken layouts, buttons, overflow, or obvious visual bugs remain.
9. README/screenshots are updated.
10. A 30–45 second showcase video is ready.

## Showcase video standard
- Minimum target: **30 seconds**.
- Start with the strongest screen immediately.
- Show the real desktop experience and all major sections/screens.
- Demonstrate meaningful interactions such as theme switching, navigation, filters, tabs, forms, or menus where available.
- Show responsive/mobile behavior clearly.
- End with project name, day number, and tech stack.
- Prefer a real working screen recording whenever the environment allows it.

## Git history
Use many **meaningful** commits that reflect actual development stages: setup → layout → components → sections → responsive work → themes → states → polish → QA. Avoid artificial one-line commit spam solely to increase the commit count.

## LinkedIn
Each project post should include the design/build focus, important features, technologies used, GitHub project link, and a concise explanation of what was improved or learned. The attached media should demonstrate the actual project rather than being only a generic promotional graphic.
